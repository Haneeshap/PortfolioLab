## Contracts and accounting

Existing `POST /api/portfolios/{id}/simulated-orders` accepts:

```json
{"assetId":1,"type":"BUY","quantity":4,"orderType":"LIMIT","limitPrice":90,"timeInForce":"DAY"}
```

`type` remains BUY/SELL; `orderType` defaults to MARKET, `timeInForce` to GTC. LIMIT requires a positive price with at most four decimals and supported numeric precision. MARKET disallows a limit. The UI defaults new tickets to DAY. Responses add `orderType`, `limitPrice`, `timeInForce`, `expiresAt`; terminal states now include EXPIRED. Existing list/detail/cancel paths remain unchanged. Terminal cancellation returns 409.

DAY ends at the next midnight in Asia/Kolkata. This is a continuous fictional market, without exchange sessions or holiday calendars. GTC has no expiration. The worker checks expiration before acceptance/fills and rolls back a fill if its quote/settlement work crosses expiration. Earlier committed fills remain settled.

A BUY reserves `quantity * ceil4((limit or current quote) * reference FX * 1.05)` in portfolio currency. A SELL reserves its unfilled shares. The 5% buffer is an explicit simulated policy, shared with the buying-power preview. Reservation admission also applies existing full-order risk limits. Actual fills still use the existing quote validation, FX conversion and risk enforcement.

Every submission, fill and cancellation locks the portfolio before its order. Legacy synchronous settlement obtains the same portfolio lock and cannot consume outstanding reservations. Before settlement, the worker reduces only the current fill's reservation inside the same transaction. Settlement checks actual cost against cash minus *all remaining reservations*. Holdings/cash are changed only by the existing settlement service. A rollback restores both reservations and settlement. Cancellation, expiration and permanent rejection release the unused remainder.

MARKET prices and FX can move beyond the buffer. A fill may use genuinely free extra cash; if insufficient, the remaining order is rejected/cancelled while earlier fills stay settled. The buffer does not guarantee execution. Temporary quote/infrastructure failures rotate the pending queue and retry later. An unmet LIMIT condition never rejects the order or blocks later eligible orders.

`GET /api/portfolios/{id}/simulated-orders/availability` returns `availableBuyingPower`, `reservedCash`, and positions with `asset_id`, `quantity`, `reserved_quantity`, `available_quantity`, from a consistent database snapshot. The Next proxy fixes the portfolio to 1. Preview is advisory and does not reserve funds.

## Streaming

`GET /api/portfolios/1/simulated-orders/events`, proxied at `/api/portfolio/simulated-orders/events`, uses SSE. Other portfolio subscriptions return 404. This preserves the existing single-user demo boundary; it does not add production authentication.

The DB trigger journals submission, status changes and cumulative fill changes in the same transaction as orders. A dedicated dispatcher reads committed rows every second; it cannot publish rolled-back changes. This reuses the database's transactional outbox pattern without coupling order visibility to Kafka notification availability. Existing Kafka consumers and notification behavior are unchanged.

`order` events include SSE `id` plus `eventId`, `portfolioId`, `orderId`, `status`, `requestedQuantity`, `filledQuantity`. All application lifecycle writes serialize on the portfolio lock, preserving cursor order within that portfolio. `Last-Event-ID` resumes scoped ordered replay, at most 100 rows per dispatch. Every connection also sends `reset`, causing an authoritative HTTP refresh even after gaps or browser restarts. Duplicate/stale events are ignored between resets; bursts coalesce. Events invalidate HTTP evidence rather than constructing balances from event payloads.

Connections have a two-minute lifetime, heartbeats and automatic native EventSource reconnection. The proxy propagates cancellation and limits connection establishment to 15 seconds. Disconnects enable serial fallback polling at five-second intervals, at most 60 requests/three consecutive read failures. Failed event-triggered HTTP/portfolio refreshes retry up to three times. Manual refresh restarts tracking. Unmount/cancel cleanup aborts reads, closes SSE and clears polling timers. RecentOrders refreshes its existing portfolio callback; the overview uses the same update controller independently.

Limitations: one-second dispatch latency; 100 simultaneous backend streams; event journal retention is currently unlimited and needs a retention policy for long-running deployments. Historical exceptions are reported rather than repaired. No live browser or database workflow was verified in this session.

## Reproduce and manually verify

Start Docker Desktop, infrastructure and services using README. Flyway applies V18-V20 on backend startup. Use the README's masked DB_PASSWORD setup for Maven tests. Prefer a separate disposable local test database with the same credentials, via `SPRING_DATASOURCE_URL`; these tests inherit the repository's PostgreSQL configuration.

```powershell
# In backend, with the configured DB_PASSWORD in this process:
.\mvnw.cmd '-Dtest=OrderLifecycleIntegrationTests' test
.\mvnw.cmd test
# In frontend:
npm.cmd run test:m34
npm.cmd run test:m35-m37
npx.cmd tsc --noEmit
npm.cmd run lint
npm.cmd run build
# In services/market-simulator:
go test ./...
```

The existing ReconciliationSqlIntegrationTests still requires a previously settled execution fixture, as documented in README. The new lifecycle tests create and clean up only their own test portfolios and process those portfolios explicitly, with other background mutations mocked.

With services running, open `/portfolio` and keep RecentOrders visible. In a separate terminal:

```powershell
$base = 'http://localhost:8080/api/portfolios/1'
$assets = Invoke-RestMethod 'http://localhost:8080/api/assets'
$asset = $assets | Where-Object currency -eq 'INR' | Select-Object -First 1
$quotes = Invoke-RestMethod 'http://localhost:8081/prices'
$quote = $quotes | Where-Object symbol -eq $asset.symbol | Select-Object -First 1
$below = [math]::Round($quote.price * 0.90, 4)
$above = [math]::Round($quote.price * 1.10, 4)
$pendingBody = @{assetId=$asset.id;type='BUY';quantity=4;orderType='LIMIT';limitPrice=$below;timeInForce='GTC'} | ConvertTo-Json
$pending = Invoke-RestMethod "$base/simulated-orders" -Method Post -ContentType 'application/json' -Body $pendingBody
Invoke-RestMethod "$base/simulated-orders/availability"
Invoke-RestMethod "$base/simulated-orders/$($pending.id)"
# The below-market order should remain ACCEPTED while price stays above its limit.
$eligibleBody = @{assetId=$asset.id;type='BUY';quantity=4;orderType='LIMIT';limitPrice=$above;timeInForce='DAY'} | ConvertTo-Json
$eligible = Invoke-RestMethod "$base/simulated-orders" -Method Post -ContentType 'application/json' -Body $eligibleBody
# Watch existing RecentOrders for ACCEPTED -> PARTIALLY_FILLED -> FILLED.
# Cancel promptly after the first partial fill to exercise a partial cancellation:
Invoke-RestMethod "$base/simulated-orders/$($eligible.id)/cancel" -Method Post
Invoke-RestMethod "$base/simulated-orders/$($pending.id)/cancel" -Method Post
Invoke-RestMethod "$base/simulated-orders/availability"
Invoke-RestMethod "$base/reconciliation"
# Separate terminal; Ctrl+C closes the stream:
curl.exe -N 'http://localhost:3000/api/portfolio/simulated-orders/events'
```

These commands change fictional demo state. Admission depends on available cash and risk policy; use a smaller quantity if necessary. A cancellation after a final fill returns 409. Try competing orders whose combined reservation exceeds available cash or shares and verify one is refused; verify available amounts return after cancelling. Keep the overview open in another tab to check portfolio refreshes. Disconnect/reconnect the backend to inspect fallback and recovery.

The Go simulator has no administrative price override endpoint. Deterministic below/above/cross/recross and expiration verification is provided by the new integration tests using injected fictional quotes; manual random-price crossing requires waiting. Do not alter historical orders to manufacture a demonstration.

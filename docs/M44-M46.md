# M44–M46: portfolio intelligence and decision workspace

Implemented on the existing `/portfolio` page: recorded-value history, deterministic P&L attribution, and hypothetical rebalance previews. The existing holdings and trade ticket remain on that page. No AI repository changes, automatic trading, new service, new scheduler, paid dependency, commits or pushes.

## Accounting audit and historical evidence

The pre-code audit and implementation plan is in `M44-M46-plan.md`.

* `transactions` is the settled activity ledger. An OMS partial fill produces a transaction; its execution receipt references that transaction. Receipts are evidence, not another financial cash flow. Pending orders, cancellations and reservations are not holdings changes.
* `holdings.historical_cost_portfolio` is remaining weighted-average basis in portfolio currency. `average_buy_price` alone is insufficient for portfolio-currency P&L, particularly after FX conversions.
* `portfolios.cash_balance` is book cash. Buying power is cash less existing order cash reservations. Reserved cash remains in equity; reserved shares remain invested assets.
* Trade cash amounts are persisted as `portfolio_amount`, using execution FX. Purchases decrease cash; sales increase it. Both settle immediately when a fill is committed by `OrderService`; the OMS has no delayed receivable/payable settlement model.
* Manual dividends and scheduled dividends have separate payment ledgers. Scheduled payments use `credited_at`, rather than their scheduled payment date, for actual portfolio income.
* There is no contribution/withdrawal ledger, historical FX series or recorded historical per-asset simulator quote series. Initial deposits cannot be reconstructed safely from today's balance. Fees are not modeled.
* Research OHLCV is explicitly generated `fictional-history-v1`. It is excluded from these portfolio calculations. Existing aggregate portfolio snapshots are actual observations but were captured without a coherent portfolio lock or position details. They remain labeled unverified.

## M44: recorded portfolio performance

The API reads persisted observations instead of applying current holdings or current cash to historical prices. UTC date buckets retain the last observation per date, plus the first observation of the selected interval. Nothing is interpolated or backfilled. A cash-only observation is valid; no observations yields `EMPTY`, not an invented zero-value history.

Periods are rolling `7D` (7 days), `1M` (30), `3M` (90), and `ALL` (bounded to 366 days). At most 368 observations are returned. All query boundaries use one database-clock timestamp per request, matching persisted timestamp precision and avoiding a just-captured database observation falling outside a JVM-clock boundary. The actual first/last observation timestamps are returned and displayed. Requested-start gaps and stale endpoints produce explicit warnings. `AVAILABLE` requires verified accounting and full requested coverage within recording tolerance; otherwise observations are `PARTIAL`.

Equity = recorded invested market value + recorded book cash. Absolute value change = observed ending equity − observed starting equity. These quantities remain distinct from investment gains when cash cannot be reconciled.

For a supported observed interval:

```
expected cash change = sale portfolio_amount − buy portfolio_amount + recorded dividends
return % = 100 × (ending equity − starting equity) / starting equity
```

The return requires two verified endpoints, endpoint position quantities matching settled transaction replay, complete position valuation totals, explained cash movement, and positive starting equity. No externally initiated cash movement exists in the audited application write paths. This is a **no-external-flow observed-interval return**, equivalent to TWR for that restricted case. It is not a general contribution/withdrawal-adjusted TWR. If cash movement is unexplained or data is insufficient, return is null. No cash movement is relabeled a contribution, withdrawal, or gain to make the calculation pass. Future external-flow functionality must add an authoritative flow ledger and valuations at flow boundaries before general TWR can be offered.

Legacy aggregate observations support the chart and absolute changes; their missing position evidence prevents verified period return/attribution. A valid return for a shorter actual interval is labeled as such even when requested coverage is partial. The API does not extrapolate it to a full selected period. Periods can be compared by requesting each preset and comparing their explicit observed intervals; unsupported periods have null return/contribution, never substituted lifetime results.

## M45: attribution

Replay transactions in `created_at, id` order, once per settled transaction, including fully closed positions:

```
buy:  quantity += fill quantity; remaining basis += portfolio_amount
sell: new quantity = previous quantity − fill quantity
      new basis = round(previous basis × new quantity / previous quantity, 4)
      realized gain += sale proceeds − (previous basis − new basis)
full close: new basis = 0
```

Decimal arithmetic uses `BigDecimal`, with the same HALF_UP remaining-basis rounding as settlement. Oversells or incomplete histories invalidate replay. Current reconstructed quantities and costs must reconcile with persisted holdings before lifetime realized/unrealized totals are published.

Current unrealized gain = current OMS-priced portfolio value − persisted remaining basis. Lifetime price P&L = realized + current unrealized; it excludes dividend income. Missing or stale current quotes yield null unrealized and total, preserving supported realized results. Current multi-currency values use the existing OMS reference FX implementation; historical snapshots remain limited to portfolios whose held assets match portfolio currency, because historical FX is unavailable.

For verified observed endpoints:

```
position contribution = ending position market value − opening position market value
                        − interval purchases + interval sales + interval credited dividends
period realized = realized-through-ending-observation − realized-through-opening-observation
```

The interval is `(opening timestamp, closing timestamp]`. Lifetime realized gains are never reused as selected-period realized gains. Beginning and ending quantities are replayed from all preceding transactions and verified against the observation details. Contributions include sold-out positions and assets bought after the opening observation. Period contributions sum to observed equity change when cash reconciles; per-position monetary rounding can produce a small aggregation residual. Realized P&L alone need not equal contribution, equity change or return. Lifetime P&L and historical endpoint P&L also describe different time boundaries. Aggregate totals become null when any required component is unavailable.

The UI displays contributors/detractors, position and aggregate figures, remaining basis, period dividends, and the accounting explanation. Unavailable values have neutral text rather than gain/loss coloring.

## M46: deterministic rebalancing preview

Targets include assets and cash, each between 0 and 100 with at most four decimals. The total must equal 100 within **0.0001 percentage points**. Unknown assets, invalid targets and portfolios are rejected. Unlisted existing holdings target zero. At most 100 assets, including all held assets, are evaluated.

1. Fetch authoritative recent OMS simulator prices and reference FX; never use catalog price fallback. Compute equity from book cash plus held quantity × quoted portfolio-currency unit value. Capture reservations in the same repeatable-read database snapshot.
2. Compute each target value as equity × target percentage / 100. Whole-share adjustment = floor(abs(target value − current market value) / quoted unit value), bounded by the OMS 13-digit quantity limit.
3. Process sales first in ascending asset-ID order, restricted to floor(held shares − reserved shares). Sales never oversell or release existing reservations.
4. Process purchases in ascending asset-ID order. Their shared budget is **initial available buying power**, excluding all hypothetical sale proceeds. Reserve-budget arithmetic uses the same 5% buffered, four-decimal ceiling unit as MARKET-order reservation logic. This deliberately leaves headroom and can leave targets unachievable even though the OMS would credit proceeds immediately after actual fills.
5. Apply the shared pre-trade policy to each ticket against both current holdings and sequential projected historical costs. Blocked tickets become HOLD with an explanation. The policy engine itself owns order-value and invested-cost concentration rules. Monetary values outside OMS precision are blocked.
6. Compute projected shares, book cash and allocations. Display target drift, residual cash, reserved funds, share/cash restrictions and policy failures. `feasible` means the exact targets are achieved within the declared allocation tolerance at estimated prices. Whole-share rounding usually leaves some drift.

The planner performs no writes, calls no order-submission method, creates no reservations and publishes no Kafka events. Its only route is a preview. It does not guarantee execution prices, fills, or future policy results; pending orders and prices can change. The existing explicit trade ticket remains authoritative. No automatic prefill or order execution connection was added.

## API contracts

Backend paths use the requested existing portfolio ID, return 404 for missing portfolios, and run under repeatable-read/read-only transactions. They do not introduce authentication beyond the repository's existing local-demo model.

| Request | Response |
| --- | --- |
| `GET /api/portfolios/{id}/performance?period=1M` | Summary, observed series and attribution in one coherent response: portfolio/currency/period, requestedFrom/asOf/earliestObservation, status, series `{id,time,cash,marketValue,equity,verified}`, startingValue/endingValue/absoluteChange/returnPct, returnMethod, attribution rows, aggregate totals, warnings and accountingMethod. Nullable unsupported figures are JSON null. |
| `POST /api/portfolios/{id}/rebalance/preview` | Body `{ "assets": { "1": 60 }, "cashPct": 40 }`. Returns equity, current cash/reservedCash/buyingPower, projectedCash/projectedCashPct, targetCashPct, feasible, adjustment rows and warnings. Rows contain current/target/projected allocations and quantities, estimated side/notional/portfolio-currency price, and constraints. |
| `GET /api/portfolio/intelligence?period=1M` | Next proxy scoped to demo portfolio 1; validates period and never caches. |
| `POST /api/portfolio/intelligence` | Next preview proxy scoped to portfolio 1; forwards only assets/cashPct. Caller-supplied execution and portfolio overrides are discarded. Malformed JSON returns 400. |

Backend history replay is bounded to 50,000 settled transactions. Exceeding that bound returns an explicit 422 rather than truncating financial history. Current positions and planner inputs are bounded to 100. The browser receives calculated analytics, not the trading ledger.

## Database and recording

Flyway V23 adds `portfolio_snapshots.positions_verified` (false for all legacy rows), `portfolio_snapshot_positions` (observed quantity, price, quote timestamp and market value), and an index for manual dividend history. Position detail is necessary because old aggregate snapshots cannot explain a portfolio's contributors and generated OHLCV is not recorded price history. No historical records or values are rewritten or backfilled.

The existing 30-second recorder now executes each portfolio capture in one transaction, acquires the same portfolio row lock used by balance writers, reads fresh cash after locking, validates quote age/currency, and atomically persists totals and position details. A missing/stale/unsupported-currency quote skips the entire observation. No new scheduler is added. Like existing aggregate snapshots, observation rows are retained; position detail increases database growth with active holdings. Retention/downsampling is not introduced silently.

## Known limits

Historical returns and contributions require two new verified observations, reconciled records and positive opening equity. Existing aggregate-only history remains partial. No fabricated historical positions, initial cash, market prices or returns are introduced. Missing historical FX prevents multi-currency recorded snapshots. There is no general external-flow-adjusted TWR, benchmark comparison, fees, optimizer or automatic trading. Prices may change between asset quote requests and before an explicit trade; preview figures are estimates. Database observation retention follows the existing recorder and should be reviewed if long-running simulations generate substantial history.
